# 校园失物招领小程序 · 需求分析

> 本文是博客正文的支撑材料（作业要求第 6、7 条），也是原型的依据。
> 需求分析按《构建之法》第 3 章和第 6 章的方法展开：先看清"用户、场景、痛点"，再定需求与取舍。

## 1. 问题从哪来

客户描述的现状是：**信息分散、容易被刷掉、跨班级看不到**。

| 现状做法 | 具体痛点 |
| --- | --- |
| 发在班级群 / 宿舍群 | 只有本班/本楼的人能看到，捡到校园卡的同学和失主往往不在同一个群 |
| 发在朋友圈 | 依赖好友关系，陌生人看不到；一天后被新动态淹没 |
| 群聊刷屏 | 之前发的信息被新消息顶上去，想再找只能翻聊天记录 |
| 口头或张贴 | 覆盖范围小，只对恰好路过的人有效 |

举例：一名同学在教学楼捡到一张校园卡，只能在班级群发一条招领信息；
而失主不在这个群里，于是这条信息等于没发出去。宿舍区、食堂、图书馆、运动场都存在同样的问题。

**一句话结论**：缺的不是"发信息的渠道"，而是"**集中发布 + 按物品名称检索**"的公开信息池。

## 2. 目标用户与典型用户画像

| 角色 | 典型用户 | 使用场景与特征 | 核心诉求 |
| --- | --- | --- | --- |
| 失主 | 大一新生小林，刚丢了一张校园卡 | 着急、当天就想找回来；不熟悉校内各种群 | 快速找到"有没有人捡到"，并立刻联系上对方 |
| 拾得者 | 大三学生阿哲，在食堂捡到水杯 | 只想尽快物归原主，不想被反复打扰、怕被误会 | 发一条标准化的招领信息，写清时间地点即可 |
| 高频浏览者 | 同班、同楼同学小陈 | 午休、睡前顺手刷一刷 | 不想翻聊天记录，按物品名称搜一下就知道有没有自己的东西 |
| 次要用户 | 宿舍管理员 / 保卫处（后期） | 集中代收、代发失物 | 批量发布与登记（本期不做） |

## 3. 用户需求（用户故事）

| 编号 | 作为…… | 我希望…… | 以便…… | 优先级 |
| --- | --- | --- | --- | --- |
| US1 | 失主 | 发布寻物信息（名称、时间、地点、描述、联系方式） | 让捡到的人看到并联系我 | P0 |
| US2 | 拾得者 | 发布招领信息 | 尽快把东西还给失主 | P0 |
| US3 | 任何同学 | 在首页按「全部 / 招领 / 寻物」浏览信息流 | 花一分钟扫一遍有没有自己的东西 | P0 |
| US4 | 任何同学 | 用物品名称等关键词搜索 | 不用翻聊天记录和群公告 | P0 |
| US5 | 任何同学 | 查看信息详情（图片、时间、地点、状态、描述、联系方式） | 判断是不是自己丢的那件 | P0 |
| US6 | 信息发布者 | 修改信息状态（待认领 / 寻找中 / 已归还 / 已找到） | 归还之后不再被反复联系 | P1 |
| US7 | 信息发布者 | 在「我的发布」里管理自己发过的信息 | 发现填错了可以改，也能删除 | P1 |

## 4. 需求取舍（本期做 / 不做）

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| 本期做 | 发布（寻物 / 招领）、浏览、搜索、详情、修改状态、我的发布 | 构成"发布 → 检索 → 联系"的最小闭环，直接解决客户困扰 |
| 本期做 | 图片上传（原型中以占位图示意） | 物品照片是判断"是不是我的东西"最有效的信息 |
| 本期不做 | 后台管理、实名认证 | 作业明确不要求；原型阶段加进来只会让流程变重 |
| 本期不做 | 即时聊天、地图定位 | 同上；联系方式先走"微信/手机号 + 复制"，后续再考虑站内消息 |
| 延后考虑 | 失物招领的分区筛选（宿舍区/教学楼）、到期自动下架 | 有价值但依赖真实数据量，等有用户量再做 |

## 5. 主要用例

| 用例 | 参与者 | 前置条件 | 主流程 | 异常 / 分支 |
| --- | --- | --- | --- | --- |
| UC1 浏览并查看详情 | 任何同学 | 已打开小程序 | 进入首页 → 看信息流或切换分类 → 点卡片 → 进详情页 → 点「联系发布者」 | 列表为空时显示"还没有信息，快来发第一条" |
| UC2 搜索物品 | 任何同学 | 已打开小程序 | 点搜索框 → 输入关键词（如"校园卡"）→ 看结果列表 → 点目标信息进详情 | 无结果 → 提示"换个关键词试试" |
| UC3 发布信息 | 失主 / 拾得者 | 已登录 | 点「＋ 发布」→ 选类型（寻物/招领）→ 填名称、类型、地点、时间 → 上传图片、填联系方式 → 点「发布」→ 发布成功 | 必填项为空 → 阻止提交并高亮提示 |
| UC4 修改信息状态 | 信息发布者 | 自己发过信息 | 我的发布 → 选一条 → 修改状态（待认领 → 已归还） | 状态为"已归还"后，详情页联系方式收起，减少打扰 |

## 6. 主要功能清单（对应作业要求第 7 条）

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| 浏览失物和招领信息 | 首页信息流，按时间倒序；顶部可按「全部 / 招领 / 寻物」切换 | P0 |
| 发布寻物信息 | 类型选「寻物」，填写丢失物品信息 | P0 |
| 发布招领信息 | 类型选「招领」，填写拾取物品信息 | P0 |
| 搜索物品 | 按物品名称等关键词搜索，命中标题与描述 | P0 |
| 查看物品详情 | 图片、时间、地点、状态、描述、联系方式 | P0 |
| 修改信息状态 | 待认领 / 寻找中 / 已归还 / 已找到 | P1 |
| 我的发布（附加） | 集中管理自己发布的信息，便于修改与删除 | P1 |

## 7. 非功能需求

* **易用**：发布一次信息不超过 3 步；首页一屏内同时看到搜索框、分类和信息流。
* **一致**：寻物统一用橙色、招领统一用绿色；状态文案只保留 4 种（待认领 / 寻找中 / 已归还 / 已找到）。
* **性能**：信息流分页加载，首屏不超过 20 条（原型阶段不做具体指标，仅约束交互）。
* **隐私**：不在描述里暴露他人隐私；联系方式默认只对登录同学可见，信息标记为"已归还"后自动收起。
